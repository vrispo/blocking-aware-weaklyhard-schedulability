# WeaklyHard: Blocking-Aware Schedulability Analysis for Weakly-Hard Real-Time Systems

## Overview

WeaklyHard is a C++ framework implementing blocking-aware schedulability analysis for real-time tasks with weakly-hard (m,k) constraints under sporadic interference. It supports preemptive and non-preemptive scheduling, Non-Preemptive Sections (NPS), Run-to-Completion Thresholds (RCT), and MILP-based verification via IBM CPLEX. The tool generates synthetic task sets, runs analysis experiments with configurable sweep parameters, and produces publication-quality plots.

## Core Components

### C++ Source Files

#### `main_experiment.cpp`

- **Purpose**: Main driver for running schedulability analysis experiments
- **Functionality**:
  - Loads experiment configuration from JSON files
  - Generates synthetic task sets with specified parameters
  - Runs schedulability analysis for each task set
  - Stores results and metadata
- **Configuration**: Accepts JSON config with generation, analysis, and experiment settings

#### `main_case.cpp`

- **Purpose**: Analyzes predefined case studies
- **Functionality**:
  - Performs detailed analysis on specific, hand-crafted task sets
  - Supports both periodic and sporadic tasks
  - Generates comprehensive analysis reports
- **Usage**: `./WeaklyHardCase <case_number> <results_directory>`
  - `case_number`: Integer 0-4, selects which predefined case study to analyze
  - `results_directory`: Path where analysis results (JSON) will be stored

#### `mixed_tasks.h/cpp`

- **Purpose**: Core task representation
- **Features**:
  - Periodic and sporadic task support
  - Preemptive and non-preemptive scheduling
  - Run-to-Completion Threshold (RCT) handling
  - Non-Preemptive Section (NPS) modeling
  - Weakly-hard (m,k) constraints
  - Utilization calculation

#### `MILP.h/cpp`

- **Purpose**: Mixed Integer Linear Programming based analysis
- **Features**:
  - Optimal schedulability testing using CPLEX solver
  - Response time analysis
  - Blocking time calculation
  - Support for complex constraint scenarios

#### `weaklydatasetJSON.h/cpp`

- **Purpose**: JSON data persistence layer
- **Functionality**:
  - Serializes/deserializes task sets to/from JSON
  - Stores analysis results in structured format
  - Handles metadata and experiment configuration

#### `c_utility.h/cpp`

- **Purpose**: Common utility functions
- **Contains**: Math helpers, file I/O, string manipulation, logging utilities

### Build System

**Makefile**:

- Configurable build for Release/Debug configurations
- Links against IBM CPLEX optimizer (required)
- Produces two executables: `WeaklyHard` and `WeaklyHardCase`
- Supports static linking for portability

## Configuration

### Configuration File Structure

Configuration files are JSON-based with three main sections:

```json
{
    "generation": {
        "force_last_unsched": true,        // Force tasksets with N_mk not hard real-time schedulable tasks that will be the weakly-hard ones
        "N": 5,                            // Number of tasks
        "N_mk": 1,                         // Number of tasks with (m,k) constraints
        "U": 0.94,                         // Total utilization (0.0 - 1.0)
        "T_min": 100,                      // Minimum task period
        "T_max": 10000,                    // Maximum task period
        "m": 3,                            // Weakly-hard m parameter
        "k": 5,                            // Weakly-hard k parameter
        "crit_sec_perc": 0                 // Critical section as % of WCET
    },
    "analysis": {
        "job_continue": true               // true: job-continue policy, false: job-discard policy
    },
    "experiment": {
        "sweep_parameter": "m",            // Parameter to vary: U, N, k, m, crit_sec_perc
        "sweep_start": 1,                  // Minimum value for sweep
        "sweep_end": 5,                    // Maximum value for sweep
        "sweep_step": 1,                   // Step increment
        "num_tasksets": 500,               // Task sets per sweep point
        "reuse_tasksets": false,           // Reuse existing task sets if true
        "results_directory": "experiments/exp01-sweep_m_preempt"
    }
}
```

### Example Configurations

Pre-configured examples in `configs/`:

- **config01-04**: Sweep m parameter (preemptive/non-preemptive)
- **config10-15**: Sweep utilization U
- **config20-21**: Sweep blocking/critical section percentage
- **config30-31**: Sweep number of tasks N
- **config40-41**: Sweep tasks with (m,k) constraints
- **config50-52**: Sweep k parameter

### Sweep Parameter Reference

The `sweep_parameter` field in the configuration accepts the following values:

| Value | Description |
| ------- | ------------- |
| `"U"` | Total system utilization |
| `"N"` | Number of tasks |
| `"m"` | Weakly-hard m parameter |
| `"k"` | Weakly-hard k parameter |
| `"crit_sec_perc"` | Critical section as % of WCET |

## Analysis Results Format

### Task Set JSON (`tasksets/m_1_0.json`)

Each task set is stored as a JSON array of task objects:

```json
[
    {
        "U": 0.1,
        "P": 1000,
        "C": 100,
        "RCT": 100,
        "NPS": 0,
        "isPreemptive": true,
        "isPeriodic": false,
        "costraint": {
            "D": 1000
        }
    },
    {
        "U": 0.06,
        "P": 5000,
        "C": 300,
        "RCT": 300,
        "NPS": 0,
        "isPreemptive": true,
        "isPeriodic": true,
        "costraint": {
            "D": 5000,
            "m": 3,
            "k": 5
        }
    }
]
```

> **Note on `isPeriodic`**: despite the name, this flag does **not** indicate the release pattern of the task (all tasks use implicit deadlines and fixed periods). Instead, `isPeriodic = true` means the task is subject to a weakly-hard (m,k) constraint and will be analyzed under the weakly-hard schedulability framework. `isPeriodic = false` means the task is treated as sporadic interference (hard real-time, no (m,k) constraint). The `m` and `k` fields appear in `costraint` only when `isPeriodic = true`.

### Results JSON (`results/m_1.json`)

Results are stored with per-task-set schedulability verdicts and timing statistics for both analysis methods (PA = priority assignment, RM = rate-monotonic):

```json
{
    "our_sum": 97.4,
    "their_sum": 95.2,
    "or_sum": 98.1,
    "our_min_t": 1200,
    "our_max_t": 85000,
    "our_avg_t": 12500.0,
    "their_min_t": 800,
    "their_max_t": 42000,
    "their_avg_t": 9800.0,
    "schedulability": [
        { "sched_our": 1, "sched_their": 1 },
        { "sched_our": 1, "sched_their": 0 },
        ...
    ]
}
```

Fields:
- `our_sum` / `their_sum` / `or_sum`: percentage of schedulable task sets for PA, RM, and PA∨RM respectively
- `our_min_t` / `our_max_t` / `our_avg_t`: min, max, average analysis time in microseconds for PA
- `their_min_t` / `their_max_t` / `their_avg_t`: same for RM
- `schedulability`: per-task-set results array; `sched_our = 1` means PA declared schedulable, `sched_their = 1` means RM declared schedulable
